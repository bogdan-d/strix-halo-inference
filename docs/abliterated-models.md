# Abliterated Flash-Next builds

Notes from November 15, 2026. The huihui patch on Gufo and Quat3rnion r2 and HT43 on Halogen have been provisioned and tested here; other candidates remain untested locally. Local results are linked below. Other numbers come from model cards and GGUF headers read with HTTP range requests; author measurements are their claims, not local results. Abliteration can reduce refusals; it does not establish the accuracy of the resulting answers.

## Picks

The Halogen and Strixite picks and the Gufo alternative derive from orcarouter's abliteration; the Gufo pick uses huihui's. None of these repositories is gated.

### Halogen: Quat3rnion r2

r2 is peonist's stock v2 checkpoint with 149 tensors replaced by the orcarouter abliteration, re-encoded in v2's own 4-bit HT format with calibrated rounding; everything else is byte-identical to stock. The file is 22 GB larger than stock v2 because it keeps the replaced payloads, unreferenced, and appends the new ones; the engine loads only referenced payloads. Its card reports, on Halogen 0.15.0: perplexity 3.134 against 3.144 for stock v2 on a 70,774-token subset of WikiText-2 raw test (KL 0.060, same top token 92.2% of the time), about 53 tok/s greedy like stock, startup about 31 s and 62.1 GiB resident weights like stock. It answered all six test prompts stock v2 refused, called a required tool correctly and read a test image. The card also lists an abliterated IQ4_XS GGUF on the same engine at 43 tok/s, about 3 minutes to start and 68.3 GiB resident.

It needs only the main file. r2 was built against peonist revision `5cc17cea1a10b502b4a5db41d8d2b1a0f22dba26` for the n-gram table and `e053f488b120b99ed2525e6ac99f68c51b3b6179` for the tokenizer and vision files; their Hugging Face LFS hashes match the files at this repository's pinned revision `506567c641cfb737e0b01c1deff10813154c5529`, which are already on disk. Select the pinned r2 package with `bin/run.sh halogen start --weights abliterated-r2 --wait` or the dashboard; its companions and prompt cache are separate from the default profile.

Pin r2 by revision. The repository's current file at the same name is a later native conversion (October 11, 66,687,678,432 bytes, SHA-256 `b5bd925fa2b44343be4a2cd328cae6b57ce7ffa2fe2cc56281717377e5a1ce8a`) made from the BF16 source with Quat3rnion's Apache-2.0 [bf16-to-hgn](https://github.com/Quat3rnion/bf16-to-hgn) converter. It has passed only offline format checks, never GPU inference, and its source-matched n-gram and vision files are not published; the author does not vouch for the stock companions with it. The repository also holds an experimental `qwen38-flash-next-ht43-abliterated.hgn`, the same abliteration applied to peonist's smaller HT43 checkpoint: 53.66 GiB against v2's 62.11 GiB, and peonist reports HT43 holds about 8 GiB less in memory. Halogen loads HT43 since 0.16. The publisher reported offline weight checks only; it has now passed local GPU inference under 0.20.4. The file changed after r2's revision (57,618,253,824 bytes, SHA-256 `2beaad7b6d5107d7abfa866b33b47287160a68b9fc45b86020dbaa884955329c` at `e7783c5`; 57,618,253,792 bytes, `e74a0d272d74f5f41c54b00b16eb62be5d691130097cbf965b90be429cd7a1fd` on `main`) while the card still lists the old hash, so pin it by revision too. Select it as `abliterated-ht43`, with a separate per-profile prompt cache.

The [local 0.20.4 trial](engine-updates.md#november-15-halogen-r2-abliterated-trial) passed full manifest hashes, inspection, full WikiText-2 comparison, live conversation/tools/cancellation and all five exact identifiers. r2 answered all five probes stock refused and used the same 78.7 GiB startup allocation. Its native verifier reports 149 false overlaps because table order differs from payload order: an independent range check found no overlaps, and a temporary table-order-only copy passed every native checksum and payload check. All inference used the unchanged pinned file. Full-corpus perplexity was 3.7891 against stock 3.7927, with 92.59% top-token agreement; the earlier card scores above used a shorter corpus. The two measured decode requests were modestly slower than stock. See the update record for limits and exact settings. Halogen's maintainers will not build refusal removal into the engine ([#239](https://github.com/peonist-ai/halogen-flash-server/issues/239)) and point to loading your own checkpoint.

### Halogen: validated HT43 trial

The [local HT43 trial](engine-updates.md#november-15-ht43-abliterated-trial) passed all manifest hashes and native verification without r2's table-order caveat. It passed live conversation, tools, cancellation and five exact identifiers, and answered the same five short probes that stock refused. Allocation was 70.2 GiB, 8.5 GiB below r2. Full WikiText-2 perplexity was 3.7673 against r2's 3.7891 and stock's 3.7927; top-token agreement was 91.14% with r2 and 90.18% with stock. Two short decode requests reached 63.34 and 63.90 tok/s. Prefer HT43 for the memory saving and passing local checks, without claiming generally better quality from the small perplexity difference. Host memory pressure differed between runs; image inputs, real coding work and long-context retrieval remain untested. Stock v2 stays the default.

### Gufo: huihui patch on the stock file

huihui's v2 GGUF repository ships a 3.56 GB patch file and a Python script that replace the `ssm_out`, `attn_output` and `ffn_down_shexp` tensors of an existing Unsloth quant, leaving the routed experts alone. Applied here on November 15 first to the October export and then to UD 3.1 `UD-Q4_K_XL`, it replaced exactly 96 Q8_0 tensors and preserved every other tensor and all metadata. The UD 3.1 copy passed Gufo 0.34.0's live conversation, tools and cancellation checks, copied five exact identifiers, answered all five probes the new stock model refused, and used the same 89.12 GiB startup allocation with the shared MTP head. The patch script was read in full and ran without network access and with read-only inputs. Output hashes and results are in the [UD 3.1 update record](engine-updates.md#november-15-ud-31-weights-and-selectable-profiles). Select it with `bin/run.sh gufo start --weights abliterated --wait` or the dashboard; both October copies have been deleted at the user's request. Quality beyond these short checks is unmeasured.

### Gufo alternative: NeosQ

NeosQ quantised the orcarouter BF16 weights with Unsloth's `UD-Q4_K_XL` type table and Unsloth's imatrix, re-split into 3 shards, and ships an MTP head built from the same weights (not Unsloth's stock head). Its header matches the stock `UD-Q4_K_XL` on disk type for type across all 1,224 tensors: experts Q4_K, Q5_1, Q8_0 and Q5_K, the n-gram table IQ4_NL, embeddings and output Q8_0, and the four tensors behind Gufo's tool-identifier corruption ([gufo-org/gufo#780](https://github.com/gufo-org/gufo/issues/780)) kept at F32. The author reports MTP on, 31 to 38 tok/s and four jailbreak probes passed on Gufo `aae1ac48`, before the #780 fix, and 32 to 38 tok/s on Halogen 0.18.15 as a GGUF; tool calling is not mentioned. The evidence is thin: only one of the four probes, a script that reads browser history, is a request a model might refuse, the runs used a 16,384-token context with thinking off, and the speeds were measured on a 4-shard layout before the re-split, after which the author repeated only a Gufo load. Its 3.85 GiB MTP head carries its own Q8_0 embedding and output tensors, which Unsloth's 2.6 GiB `shared` head takes from the trunk, so Gufo should need about 1.2 GiB more than the stock model's 89 GiB at full context with MTP. Halogen also reads this layout as a GGUF with its own draft head, but that is not a route worth taking here: its [GGUF guide](https://github.com/peonist-ai/halogen-flash-server/blob/v0.20.4/docs/gguf.md) puts `UD-Q4_K_XL` at 78 to 80 GiB held in RAM against about 62 GiB for v2, with slower decode, and lists a known issue where a K-quant GGUF can return an empty reply when requests overlap ([#172](https://github.com/peonist-ai/halogen-flash-server/issues/172), closed as not planned on November 3).

### Strixite: ngkzngkz

ngkzngkz converted orcarouter's weights with Strixite's own [conversion recipe](https://github.com/shawnshekari/strixite/blob/main/docs/tools.md) (v0.2.4, vision tower added with v0.3.0). The files match the layout and sizes of the pinned `wemoh` package: 65.86 GiB of weights with Q4 routed experts, a 48.28 GiB Q8 n-gram table and a 0.84 GiB BF16 vision tower. Its weights file declares strixw format version 4 (converter commit `58c7304`), and Strixite 0.7.0 reads versions 1 to 4 ([`formats/strixw.hpp`](https://github.com/shawnshekari/strixite/blob/v0.7.0/formats/strixw.hpp)); the pinned `wemoh` weights on disk are version 3, so the format gate passes, though nobody has published a run. The n-gram table is probably the same data as the `wemoh` table on disk: the abliteration does not touch it, the two headers differ only in the converter commit, and six of seven 1 MiB ranges sampled across the file are byte-identical (the last one, at the end of the file, differs, as do the SHA-256 hashes). Whether Strixite accepts the local table beside these weights is untested; if it does, the download drops by 48 GiB. Strixite's `tools/convert_qwen4exp.cpp` can convert a BF16 source locally instead.

huihui's `patch-unsloth` tool is the Gufo pick, [above](#gufo-huihui-patch-on-the-stock-file). It patches by tensor type, so it should also apply to the UD 3.1 files: their `ssm_out`, `attn_output` and `ffn_down_shexp` tensors are Q8_0 or Q6_K, and the patch carries Q8_0, Q6_K, Q5_K and BF16 entries. `gguf` 0.19.0 from PyPI, which ran the patch here, does not know GGML `Q2_0`, so patching UD 3.1 `UD-IQ4_XS` needs a `gguf` build that does.

Below `UD-Q4_K_XL`, Gufo needs the [`flash_next_iq` extension](gufo-extensions.md#community-options), which adds Unsloth's `UD-IQ4_XS` layouts to stock Gufo 0.34.0 at about 80.8 GiB of device memory by its README. huihui v2's `unsloth-UD-IQ4_XS` folder (87.25 GiB) matches Unsloth's October `UD-IQ4_XS` at `38bb39ee` type for type across all 1,224 tensors, and the extension lists that export as supported, so it is the abliterated candidate for that route; nobody reports running it. orcarouter's IQ4_XS is unlikely to load there: its dense trunk is IQ4_XS, Q5_K and IQ4_NL and the four #780 tensors are IQ4_XS, while the extension's trunk code takes F32, Q8_0 and Q6_K.

The most downloaded abliterated builds fit neither engine. [SC117/Qwen3.8-Flash-Next-GSQ-RCO-abliterated-GGUF](https://huggingface.co/SC117/Qwen3.8-Flash-Next-GSQ-RCO-abliterated-GGUF) transplants orcarouter's tensors into GSQ-RCO quants; even its largest tier, IQ3_S, contains IQ3_XXS, IQ2_S and Q2_0 tensors, which stock Gufo's expert list excludes and Halogen refuses by name (the IQ2 family). [agentionai/Qwen3.8-Flash-Next-Gyro-abliterated-Huihui-GGUF](https://huggingface.co/agentionai/Qwen3.8-Flash-Next-Gyro-abliterated-Huihui-GGUF) uses trellis types that need Strata, strix-llama.cpp or agentionai's llama.cpp. Neither was checked against the `flash_next_iq` extension.

**Halogen 0.20.4** reads GGUFs whose tensors use the IQ4_NL, IQ4_XS, IQ3_S or Q4_0 family, Q8_0, Q6_K, Q4_K, Q5_K or Q5_1, and Q5_0 except on the gate/up experts ([GGUF guide](https://github.com/peonist-ai/halogen-flash-server/blob/v0.20.4/docs/gguf.md)). It refuses Q4_1, Q2_K, Q3_K and the IQ2 and IQ1 families by name, and refuses a file re-encoded from an already quantised one, which likely excludes SenseiHans. It uses its own draft head with any GGUF trunk, and its `convert` mode writes a GGUF to a native `.hgn` once. orcarouter's own IQ4_XS GGUF (90.77 GiB plus a 3.85 GiB MTP draft) uses IQ4_XS and IQ4_NL, Q5_K on `attn_qkv` and `attn_v` and a Q6_K output, all types Halogen reads, so it should load, with the Q5_K dense tensors staged as bf16 on the GPU; `wy2pay/Qwen3.8-Flash-Next-abliterated-GGUF-IQ4XS` is a byte-identical ungated copy. r2's card measured an abliterated IQ4_XS GGUF on Halogen as slower, slower to start and larger in memory than r2, and this file keeps the four #780 tensors at IQ4_XS, so tool calling would need its own check. [johnlockejrr/Swift-1.5-Qwen3.8-Flash-Next-heretic-HGN](https://huggingface.co/johnlockejrr/Swift-1.5-Qwen3.8-Flash-Next-heretic-HGN) is a native checkpoint of a different fine-tune (Swift 1.5, Swift Open License 1.0), not yet run in Halogen by its author. Other native conversions exist and none beats r2 on evidence. [johnlockejrr/Huihui-Qwen3.8-Flash-Next-abliterated-HGN](https://huggingface.co/johnlockejrr/Huihui-Qwen3.8-Flash-Next-abliterated-HGN) and its [v2](https://huggingface.co/johnlockejrr/Huihui-Qwen3.8-Flash-Next-abliterated-v2-HGN) are complete 66.7 GB v2 bundles with their own n-gram, vision and tokenizer files, made with bf16-to-hgn on November 2 to 4; their cards record no load in the engine. Ae55667, tatianyi, davenetdev and DogEasy also publish abliterated `.hgn` files (an overlay for the deprecated w4b checkpoint, and single files of 102 to 132 GB); these were seen in file listings only and not evaluated.

**Strixite** reads only its own strixw format; besides ngkzngkz's build, Hugging Face lists strixw conversions of Swift 1.5 and ThinkingCap, both fine-tunes.

## Trial plan

1. Completed: download the r2 file by revision into a new directory beside the stock checkpoint, verify its size and SHA-256, and run Halogen's `verify`, `inspect` and `ppl` against the stock checkpoint.
2. Completed: start Halogen with the `abliterated-r2` weight profile, then run the health check, a real generation, `tests/live.py`, a refusal probe and the startup allocation, and record the results in the update record.
3. Completed: for lower memory, repeat steps 1 and 2 with the HT43 file pinned at `e7783c5`, comparing `ppl` and resident memory with r2.
4. Gufo is covered by the huihui patch run on November 15. Try NeosQ only if the same orcarouter abliteration is wanted on every engine, and include tool calling, since its author did not test it and #780 showed that a quant recipe (four small tensors stored as Q8_0) can corrupt copied identifiers on Gufo.

The launcher and dashboard share named weight profiles for every engine; see [weight profiles](weight-profiles.md). New trials add a catalog entry and a pinned manifest. The full sequence is in `.scratch/abliterated-trials/`.
